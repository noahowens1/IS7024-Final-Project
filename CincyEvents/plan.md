# Event Categories Implementation Plan

## 1. Objective

Implement the Event Categories feature described in `spec.md` using ASP.NET Core Razor Pages and static in-memory data.

The feature will provide:

- A category listing page.
- Five clickable category cards.
- Dedicated category detail pages.
- Invalid-category handling.
- Responsive Bootstrap styling.
- Keyboard-accessible navigation.
- No database or external service dependency.

No application code will be implemented during the Plan phase.

## 2. Files to Create

### `CincyEvents/Models/EventCategory.cs`

Create a simple immutable model representing one event category.

The model should contain:

- A stable identifier or slug.
- A display title.
- A short description.

The stable identifier should be URL-safe and independent of the display title. Proposed identifiers:

| Identifier | Display title |
| --- | --- |
| `music-concerts` | Music & Concerts |
| `sports` | Sports |
| `food-dining` | Food & Dining |
| `arts-culture` | Arts & Culture |
| `festivals-community` | Festivals & Community |

### `CincyEvents/Services/CategoryCatalog.cs`

Create a static category catalog that contains the five supported categories.

Responsibilities:

- Expose the complete read-only category collection.
- Find a category by its stable identifier.
- Return no category when the identifier is missing or unknown.
- Avoid database, Entity Framework Core, configuration, or external API dependencies.

The catalog should be the single source of truth for category titles and descriptions. Both the listing page and detail page should read from this catalog to prevent duplicated or inconsistent data.

### `CincyEvents/Pages/Categories/Index.cshtml`

Create the Razor markup for the category listing page.

Responsibilities:

- Set an appropriate page title.
- Display a page heading and introductory text.
- Iterate over the categories supplied by the page model.
- Render one Bootstrap card per category.
- Include each category title and description.
- Provide a Razor Page link to the corresponding detail page.

### `CincyEvents/Pages/Categories/Index.cshtml.cs`

Create the page model for the category listing page.

Responsibilities:

- Load the read-only category collection from `CategoryCatalog`.
- Expose the categories to `Index.cshtml`.
- Avoid database access or unnecessary request handlers.

The page should use the existing `CincyEvents.Pages` namespace convention or the namespace generated by the existing Razor Pages folder structure.

### `CincyEvents/Pages/Categories/Details.cshtml`

Create the Razor markup for an individual category detail page.

Responsibilities:

- Display the selected category title.
- Display the selected category description.
- Use the existing shared layout.
- Provide a link back to the category listing page.

### `CincyEvents/Pages/Categories/Details.cshtml.cs`

Create the page model for the category detail page.

Responsibilities:

- Accept the category identifier as a route parameter.
- Look up the identifier in `CategoryCatalog`.
- Expose the matching category to the Razor page.
- Return a not-found result for an unknown identifier.
- Avoid redirecting an invalid identifier to an unrelated category.

The page route should use a stable identifier, such as:

`/Categories/{id}`

## 3. Files to Modify

### `CincyEvents/Pages/Shared/_Layout.cshtml`

Add a navigation link to the category listing page.

The link should use the Razor Pages tag helper rather than a hard-coded URL:

- Page target: `/Categories/Index`
- Visible text: `Categories`

The existing Bootstrap navigation structure should be preserved.

### `CincyEvents/Pages/Index.cshtml`

Optionally add a prominent link or call-to-action to the category listing page so users can discover the feature from the home page.

If the home page remains outside the feature scope, this file does not need to be modified. The primary navigation link in `_Layout.cshtml` is sufficient for access.

### `CincyEvents/wwwroot/css/site.css`

Modify only if the existing Bootstrap utility classes do not provide sufficient presentation for the cards.

Custom CSS should be limited to feature-specific improvements such as:

- Equal-height cards.
- Card hover indication.
- Consistent card link presentation.
- Focus-state visibility.

The initial implementation should prefer Bootstrap classes and avoid unnecessary custom CSS.

## 4. Static Category Data

The five categories will be represented by `EventCategory` objects stored in `CategoryCatalog`.

The catalog will expose a read-only collection containing:

1. Music & Concerts
2. Sports
3. Food & Dining
4. Arts & Culture
5. Festivals & Community

Each entry will have:

- A URL-safe identifier.
- A display title.
- A short description.

The data will be initialized in application code. It will not be loaded from:

- A relational database.
- Entity Framework Core.
- A `DbContext`.
- A JSON API.
- An external event provider.
- User input.

The catalog will be shared by both Razor Page models so that category cards and detail pages always use identical values.

## 5. Category Listing Page

The category listing page will be available at:

`/Categories`

The Razor Page model will expose all five categories to the view.

The view will use a responsive Bootstrap grid. Each category will be rendered as a card using classes such as:

- `row`
- `g-4`
- `col-12`
- `col-md-6`
- `col-lg-4`
- `card`
- `h-100`
- `card-body`

Each card will contain:

- A heading containing the category title.
- A paragraph containing the category description.
- A visible link to the category detail page.

The card link will be generated with the Razor Pages `asp-page` and `asp-route-id` tag helpers.

## 6. Category Detail Navigation

Each listing card will navigate to a detail URL using the category's stable identifier.

Example URLs:

- `/Categories/music-concerts`
- `/Categories/sports`
- `/Categories/food-dining`
- `/Categories/arts-culture`
- `/Categories/festivals-community`

The detail Razor Page will declare a route template containing the identifier.

The detail page model will:

1. Receive the route identifier.
2. Search the static category catalog.
3. Store the matching category for display.
4. Return `NotFound()` if there is no match.

The detail page will include a link back to `/Categories`.

No JavaScript will be required for navigation.

## 7. Invalid Category Identifiers

Invalid identifiers will be handled in the detail page model.

Examples of invalid requests include:

- `/Categories/unknown`
- `/Categories/not-a-category`
- A missing identifier.
- An identifier that differs from a supported value.

For an invalid identifier:

- The page model will not select a default category.
- The application will return a not-found result.
- The existing ASP.NET Core error handling behavior will be used unless a later implementation decision adds a dedicated user-friendly not-found page.

An invalid identifier must never display another category's information.

## 8. Bootstrap and Responsive Styling

The shared layout already includes Bootstrap CSS and JavaScript. No new UI framework or package is required.

Bootstrap will be used to:

- Arrange cards in a responsive grid.
- Provide consistent spacing.
- Maintain equal-height cards.
- Style headings, links, and card content.
- Support mobile, tablet, and desktop layouts.

Proposed layout behavior:

- One card per row on narrow screens.
- Two cards per row on medium screens.
- Up to three cards per row on larger screens.

The implementation should reuse the existing classes and stylesheet conventions before adding custom CSS.

## 9. Accessibility

Accessibility requirements will be addressed as follows:

- Use semantic headings for the listing and category detail pages.
- Use real anchor elements for navigation instead of clickable non-interactive elements.
- Ensure each category link has an accessible name based on the category title.
- Keep visible link text descriptive.
- Preserve visible keyboard focus indicators.
- Avoid relying on color, hover, or card styling alone to communicate interactivity.
- Use sufficient text contrast through existing Bootstrap styles.
- Keep the category descriptions available as normal text for screen readers.
- Verify that keyboard users can move through and activate every category link.

The entire card may be visually styled as clickable, but the semantic navigation control must remain a real keyboard-accessible link.

## 10. Testing and Debugging

### Build validation

After implementation:

1. Restore the project.
2. Build the solution or project.
3. Confirm that Razor compilation succeeds.
4. Confirm that no database or package dependency was introduced.

### Manual functional tests

Verify the following routes and behaviors:

- `/Categories` displays all five category cards.
- Each card displays the correct title.
- Each card displays a short description.
- Selecting each card navigates to the correct detail URL.
- Each detail page displays the matching title and description.
- The return link navigates back to the category listing.
- Invalid identifiers return a not-found result.
- The feature works without a database connection.

### Responsive tests

Use browser developer tools to verify:

- Mobile layout.
- Tablet layout.
- Desktop layout.
- Cards remain readable and usable at each viewport width.
- No horizontal scrolling is introduced by the feature.

### Accessibility tests

Verify:

- All category links are reachable with the Tab key.
- Focus indicators are visible.
- Links activate with Enter.
- Headings appear in a logical order.
- Link text remains meaningful when read independently.
- The category pages remain usable without JavaScript.

### Debugging approach

If a page does not load:

1. Confirm the Razor Page file location and route declaration.
2. Confirm the route identifier matches the catalog identifier.
3. Set a breakpoint in the detail page model's request handler.
4. Inspect the received route parameter.
5. Verify the catalog lookup result.
6. Confirm that `NotFound()` is only returned for unsupported identifiers.

If category content is inconsistent:

1. Confirm both pages use `CategoryCatalog`.
2. Verify that category titles and descriptions are not duplicated in the Razor views.
3. Check that the stable identifier is unique.

If the layout is incorrect:

1. Confirm the page uses the existing `_ViewStart.cshtml`.
2. Verify that `_Layout.cshtml` still loads Bootstrap and `site.css`.
3. Inspect responsive Bootstrap column classes in the browser.

## 11. Implementation Constraints

- Use Razor Pages, not MVC controllers or Blazor components.
- Target `.NET 8`.
- Do not add a database.
- Do not add Entity Framework Core.
- Do not create a `DbContext`.
- Do not add external APIs.
- Keep category data static.
- Follow the existing four-space C# indentation and Razor formatting.
- Reuse the existing shared layout.
- Do not create `constitution.md`.
- Do not create `tasks.md` during the Plan phase.
